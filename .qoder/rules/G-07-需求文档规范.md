# G-07: 需求文档编写规范

## 定位

本规范约束**写需求文档的AI**。

用户给想法 -> 你生成需求文档 -> 开发AI读文档开发

文档质量直接决定开发AI能否正确执行。

---

## 生成流程

```
用户给想法
  -> 判断级别 L1/L2/L3
  -> 追问缺失信息（见追问清单）
  -> 生成需求文档
  -> 用户确认/修改
  -> 交付开发AI
```

### 追问清单

用户没说清的，必须追问：

- 有哪些实体？每个实体管什么？
- 实体之间的关系（一对多/多对多）？
- 谁操作？什么角色？什么权限？
- 列表怎么搜？怎么排？怎么分页？
- 枚举值有哪些？每个值什么含义？
- 做什么？不做什么？

### 推断规则

用户回答后仍有不明确的：

- 字段推断标准字段（id, name, status, create_time, update_time, is_deleted）
- 枚举推断常见值（0=禁用, 1=启用）
- 接口按 RESTful CRUD 标准生成
- 页面按列表+弹窗标准布局
- 不确定处标记 `【待确认】`

## 文档结构

```
# [REQ-XXX] 项目/功能名称

## 0. 元信息

| 编号 | REQ-XXX |
| 级别 | L1/L2/L3 |
| 优先 | P0/P1/P2/P3 |
| 技术栈 | 后端XX/前端XX/数据库XX |
| 状态 | 待确认/已确认 |

## 1. 概述

### 目标
一句话：解决什么问题

### 用户角色
| 角色 | 权限范围 |
|------|---------|

### 核心实体
- 实体A
- 实体B
- 关系：A和B的关系

## 2. 实体定义

每个实体一张表：

### 实体名 (表名)

| 字段 | 类型 | 必填 | 默认 | 说明 | 索引 |
|------|------|------|------|------|------|

枚举：
- 字段名: 值1=含义, 值2=含义

关联（逻辑关联，禁止外键约束，与G-03一致）：
- user_id -> users.id（应用层控制，不加 FOREIGN KEY）

## 3. 接口定义

标准 CRUD：
```

GET /api/v1/{resource} 列表
GET /api/v1/{resource}/:id 详情
POST /api/v1/{resource} 创建
PUT /api/v1/{resource}/:id 更新
DELETE /api/v1/{resource}/:id 删除

```

每个接口写清：
```

接口: 名称
方法: GET/POST/PUT/DELETE
路径: /api/v1/xx
权限: 登录/管理员/...

参数:
| 参数 | 类型 | 必填 | 说明 |

参数校验:（仅POST/PUT）
| 字段 | 规则 |

响应: { code, message, data }
错误码: 0=成功, 1001=参数错误, ...（详见 G-10）

```

## 4. 前端页面

### 页面清单
| 页面 | 路由 | 说明 |
|------|------|------|

### 列表页
字段：
| 字段 | 列名 | 可排序 | 可搜索 | 渲染 |
|------|------|--------|--------|------|

操作：新增/编辑/删除（标注谁可见）

交互：
```

进页面 -> 加载 -> 搜索/筛选 -> 新增弹窗 -> 编辑回填 -> 删除确认

```

### 表单字段
| 字段 | 控件 | 必填 | 校验 | 默认 |
|------|------|------|------|------|

## 5. 权限

| 操作 | 角色 |
|------|------|

## 6. 不做什么

1. 不做XX
2. 不做XX

## 7. 影响分析 (L3)

| 模块 | 影响 | 说明 |
|------|------|------|

## 8. 验收标准

- [ ] 功能项1
- [ ] 功能项2
- [ ] 边界情况
- [ ] 构建通过
```

## L1 快速版

```
# [REQ-XXX] 标题

级别: L1

改动位置: 文件路径
改动内容: 改什么
期望效果: 改完什么样
```

## Bug 模板

```
# [BUG-XXX] 标题

复现: 1. 2. 3.
期望: 应该怎样
实际: 实际怎样
报错: 错误信息

验收:
- [ ] 复现步骤不再触发
- [ ] 正常功能不受影响
```

---

## 质量要求

### 必须做到

1. 字段名用数据库风格（snake_case），不用业务别名
2. 枚举值写全，不留"等"
3. 接口路径 RESTful，不用动词
4. "不做什么"必须写，防止开发AI越界
5. 验收标准具体可执行
6. 不确定处标 `【待确认】`

### 禁止做到

1. 不生成文档直接让开发AI开发
2. 文档没确认就催开发
3. 自行推断业务逻辑不标记待确认
4. 跳过"不做什么"
5. 用"可能/大概/最好"等歧义词
6. 混用命名风格

---

## 与开发AI的交接

文档生成并确认后：

1. 将完整文档交给开发AI
2. 开发AI输出技术方案
3. 用户确认方案
4. 开发AI按文档+方案开发
5. 开发完成后对照文档验收标准逐项过
