# G-00: 快速参考

> 改代码前看一遍，避免低级错误

## 改代码前必须做

```
1. grep_code 搜现有实现
2. read_file 读要改的文件
3. grep_code 搜所有调用方
4. 输出影响分析（L2/L3）
5. 用户确认后再改
```

## 工具选择

| 场景      | 用              | 不用          |
| --------- | --------------- | ------------- |
| 读文件    | read_file       | cat/head/tail |
| 改文件    | search_replace  | sed/awk       |
| 搜内容    | grep_code       | grep/rg       |
| 找文件    | search_file     | find/ls       |
| 写文件    | create_file     | echo/heredoc  |
| 简单命令  | run_in_terminal | -             |
| 多步/并行 | Agent           | 手动逐步      |

## 禁止（红线）

- 不读代码就改
- 不搜现有实现就写新功能
- 改 API 不改调用方
- 硬编码密钥
- 吞掉错误
- 编造不存在的 API
- 顺便重构不相关代码
- 自行引入新依赖
- 修改接口签名
- **自行推断业务逻辑**：不要替用户决定"什么更安全"、"什么更合理"，用户说怎么实现就怎么实现
- **假设用户场景**：不要假设"用户可能修改ID"、"用户可能删除列"等场景，按用户明确的需求实现
- **过度设计**：不要为了"最安全"、"最健壮"添加用户没要求的校验逻辑

## 改完必须检查

```
□ 能编译/通过类型检查
□ 所有 import 能解析
□ 没有占位代码
□ 错误处理了
□ 搜了所有调用方确认没影响
□ 搜索代码库，发现同类问题一起修复
  → 同模块其他位置：当前文件/模块中是否有相同模式的问题（如其他字段也用错检索方式）
  → 其他模块相同功能：其他模块的同类功能是否有同样问题（如其他导入导出、其他表单）
  → 输出发现清单：列出所有发现的问题，用户确认后再一起改
```

## 任务分级

| 级别 | 定义               | 动作                                  |
| ---- | ------------------ | ------------------------------------- |
| L1   | 简单明确，无风险   | 直接执行                              |
| L2   | 需要确认方案       | 先输出方案，用户确认后执行            |
| L3   | 删除、改接口、重构 | 必须输出影响分析+方案，用户确认后执行 |

## 决策树

```
收到任务 → 判断类型
├── 写新功能？→ L2/L3 → 输出方案 → 用户确认 → 执行
├── 改 Bug？→ 复现 → 定位 → 最小修复 → 验证
├── 改逻辑？→ 影响分析 → 同步改调用方 → 验证
└── 不明确？→ 列出假设 → 问用户
```

## 编码原则（重要）

- **优先复用**：已有功能能用的直接调用，不要重复造轮子
- **DRY 原则**：出现 2 次以上相同逻辑 → 提取为函数/组件（详见 G-02）
- **简单 > 复杂**：小功能用简单写法实现，不要引入过度抽象
- **就地扩展**：优先在现有文件中添加代码，不要动不动就新建文件。当文件接近 G-02 大小上限（如已达 80%）时应新建文件拆分
- **3 行能解决的不写 30 行**：避免为了一个小功能创建额外的模块/文件

- **按代码逻辑实现，不按猜测实现**：字段语义、更新逻辑、检索方式必须以代码/数据库实际定义为准，禁止自行推断业务含义（如把 carousel_num 当成 id），不确定时列出字段定义和用途请用户确认

> 完整开发工作流见 G-01

## 会话闭环提醒

**任何一次回复结束前，检视当前任务是否已闭环**（子版本交付、里程碑达成、用户说"好的/OK/就这样"）。
**只要闭环了，必须在回复末尾输出**：

```
请读取项目文档，继续 [具体任务]
```

这句用代码块包起来让用户一键复制。修 Bug 补测试不触发，其余都触发。详见 G-13。

## 角色定位

根据任务自动识别身份（架构师/开发者/审查者/修复者），详见 G-13 会话协作规范。

```
安全 > 正确性 > 可维护性 > 性能
```
