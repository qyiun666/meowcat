# G-06: 测试规范

## 测试类型

| 类型     | 目标          | 工具                       |
| -------- | ------------- | -------------------------- |
| 单元测试 | 函数/组件逻辑 | Go testing, pytest, Vitest |
| 集成测试 | 多模块协作    | 按需添加                   |
| E2E 测试 | 完整流程      | 按需添加                   |

## 单元测试规范

- 文件名: `*_test.go`, `test_*.py`, `*.test.ts`
- 覆盖: 正常路径 + 异常路径
- 独立: 每个测试独立，不依赖执行顺序
- 快速: 单元测试应在毫秒级完成

## TDD

1. 写测试（失败）
2. 写最小实现（通过）
3. 重构（保持通过）

## Mock

- 外部依赖必须 Mock（数据库、API、文件系统）
- Go: mockgen
- Python: unittest.mock
- TS: vitest mock

### Mock 详细规范

- 外部依赖（API、数据库、文件系统）必须 Mock
- 不要 Mock 被测试的核心逻辑
- 使用真实数据结构，避免过度简化的 Mock
- 集成测试中尽量减少 Mock，使用真实依赖

```typescript
// 正确 - Mock 外部 API
const mockFetch = vi.fn().mockResolvedValue({
  json: () => Promise.resolve({ id: 1, name: "Test" }),
});
global.fetch = mockFetch;

// 错误 - Mock 核心业务逻辑
const mockCalculate = vi.fn().mockReturnValue(100);
```

## 测试命名约定

- 测试文件：与源文件同名 + `.test` 或 `.spec` 后缀
- 测试套件：`describe('被测试单元名称')`
- 测试用例：`it('should + 预期行为')` 或 `test('does something')`
- 使用业务语言，不要技术黑话

```typescript
// 正确示例
describe("UserService", () => {
  describe("createUser", () => {
    it("should create user with valid email", () => {});
    it("should throw ValidationError when email is invalid", () => {});
    it("should hash password before saving", () => {});
  });
});

// 错误示例
describe("tests", () => {
  it("test1", () => {});
  it("works", () => {});
});
```

## 测试数据管理

- 使用工厂函数或 Fixture 生成测试数据
- 每个测试独立准备数据，避免共享状态
- 测试后清理数据（数据库、文件、缓存）
- 使用有意义的测试数据，不要随意字符串

```typescript
// 正确 - 工厂函数
function createTestUser(overrides = {}) {
  return {
    id: "test-user-1",
    email: "test@example.com",
    name: "Test User",
    ...overrides,
  };
}

it("should update user email", () => {
  const user = createTestUser();
  // 测试逻辑
});

// 错误 - 所有测试共享同一个用户对象
const sharedUser = { id: 1, email: "a@b.c" };
```

## 边界条件和异常测试

- 测试空值、null、undefined
- 测试边界值（0、负数、最大值、最小值）
- 测试异常输入和错误处理路径
- 测试并发和竞态条件（如适用）

```typescript
describe("divide", () => {
  it("should divide two positive numbers", () => {
    expect(divide(10, 2)).toBe(5);
  });
  it("should throw error when dividing by zero", () => {
    expect(() => divide(10, 0)).toThrow("Division by zero");
  });
  it("should handle negative numbers", () => {
    expect(divide(-10, 2)).toBe(-5);
  });
});
```

## 测试隔离性

- 每个测试独立运行，不依赖执行顺序
- 使用 `beforeEach`/`afterEach` 清理状态
- 避免修改全局变量或单例
- 并行运行测试时不应失败

## 覆盖率

| 项目类型 | 最低覆盖率 | 关键路径 |
| -------- | ---------- | -------- |
| Web 应用 | 70%        | 90%+     |
| CLI 工具 | 80%        | 95%+     |
| 库/SDK   | 85%        | 100%     |

- 核心逻辑: ≥80%
- 工具函数: ≥60%
- 新增代码覆盖率不得低于现有基线

## 测试分层策略

遵循测试金字塔原则：

```
     /\     E2E Tests (10%)
    /  \    Integration Tests (20%)
   /____\   Unit Tests (70%)
```

- **单元测试（70%）**: 快速、隔离、针对单个函数/类
- **集成测试（20%）**: 验证模块间交互
- **E2E 测试（10%）**: 关键业务流程端到端验证
- 避免过度依赖 E2E 测试（慢、脆弱、维护成本高）

## 测试性能要求

- 单元测试：每个 < 100ms
- 集成测试：每个 < 1s
- E2E 测试：每个 < 10s
- 整体测试套件 < 5 分钟
- 慢测试应异步化或并行化

## CI 集成

- 提交前跑本地测试
- CI 流水线: 构建 → 测试 → 安全检查
- 测试失败阻断合并
- 新增代码覆盖率不得低于现有基线
